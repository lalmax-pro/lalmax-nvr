# P4 多档共享解码对照实验（2026-10-30）

## 结论和部署决定

本轮 **不启用生产多档共享解码**。共享解码在本机 4 秒小样本中总 CPU 较低，但在 40 秒重复样本中总 CPU 反而略高，墙钟耗时也更长。不能依据小样本声称持续性能收益。现有每个 Profile 独立处理、同规格输出共享物理任务的行为保持不变。

此文件记录的是隔离环境中对算法路径的对照，不是设备性能承诺，也不替代真实摄像机或 ARM/GPU 压测。

## 被测环境

- Linux x86_64（隔离容器）
- FFmpeg 7.1.5（Debian 打包版本）
- 合成 640×360 30fps H.264 源，4 秒文件
- 两档输出：320×180、160×90，libx264 ultrafast
- 同源重复循环 10 次获得约 40 秒媒体输入
- 串联式共享实验：一个 FFmpeg 进程 `split=2`，两个缩放/编码分支
- 独立实验：两个并行 FFmpeg 进程，各自解码同一 MP4 输入
- 使用 `/usr/bin/time` 的 wall、user、sys、max RSS（KiB）测量；无宿主系统负载基线

## 实际记录

| 输入 | 架构 | 墙钟秒 | user+sys CPU 秒 | 最大 RSS KiB |
|---|---|---:|---:|---:|
| 4s | 共享一个进程 | 0.30 | 0.49 | 46,068 |
| 4s | 两独立进程 | 0.26（并发完成） | 0.67（两进程合计） | 85,960（分别 43,704 / 42,256） |
| 40s | 共享一个进程 | 1.45 | 3.58 | 46,656 |
| 40s | 两独立进程 | 0.97（并发完成） | 3.43（两进程合计） | 86,380（分别 43,832 / 42,548） |

注意：将两个独立进程的 RSS 相加会重复计入共享动态库页面；不能直接解释成真实物理内存节省。不同 FFmpeg 命令的线程调度也使小样本墙钟值不具统计意义。

## 故障隔离与风险

共享解码进程意味着任一输入解码中断或共享进程崩溃将同时影响所有档位；独立进程仅影响所在档位。两条路径均需要独立的输出就绪探测、故障码、消费者生命周期、并发容量控制及超时关闭。共享解码方案还需解决：某档动态取消不重启其他档、分支背压、异构硬件编码器和输出帧率协商、音频同步与 RTMP 回灌身份隔离。

## 后续启用门槛（当前未满足）

1. 实体 H.265 相机与高码率 RTSP 长期测试，测量 CPU/PSS、端到端延迟和输出健康；
2. 3 档 1080p/720p/360p 与原有独立进程做三次以上稳态对照；
3. 单档故障、重建、全部断流、消费者撤销时验证其余档不受污染；
4. 故障影响半径和净收益可接受，且明确配置开关/回退路径后才允许实现并上线共享解码调度。

目前结论为 **暂不引入多档共享解码**；维持独立档位任务和同配置物理去重，是有证据支持的保守决策。
