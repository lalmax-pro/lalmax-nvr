# feat: 通用实时转码能力（FFmpeg / GStreamer、本地与 Docker）

> 已于 2026-10-26 创建：[GitHub Issue #66](https://github.com/lalmax-pro/lalmax-nvr/issues/66)。本文为创建正文的本地备份，后续实施进展以线上 Issue 为准。

## 背景

关联 #46。此前 HA 集成中转码按范围约定暂缓；本 Issue 单独跟踪通用实时转码，不以 HA 为功能边界，也不改变 #46 其他事项的验收结论。

转码是 NVR 的媒体基础能力，供 NVR 网页、Home Assistant、外部播放器以及后续录像/转推共用。原始流默认保留，按需配置派生输出，消费者不自行启动编码器。

## 架构设计文档

已准备仓库文档 `docs/zh/transcoding-design.md`（2026-10-26，Proposed）。

**文档尚未提交/推送时，此路径仅表示待纳入仓库的位置，不代表线上链接已经可用。** 文档 PR 合并后，在此补充永久链接及提交版本。

核心架构：

```text
统一媒体源 / lalmax 原始流
       ├── 原流播放与录像
       └── TranscodeManager
              ├── FFmpeg Backend
              └── GStreamer Backend
                       ↓
                 lalmax 派生输出
                       ↓
             NVR / HA / 外部播放 / 录像 / 转推
```

## 设计原则

- 通用对象：SourceRef、Profile、Job、Variant、DemandLease。
- 模板和任务独立管理；HA 只引用输出，源身份、云台和事件不变。
- 相同源和有效模板复用任务；取消一个消费者不影响其他消费者。
- FFmpeg 默认后端，GStreamer 可选；公共层负责配额、重试、状态与权限。
- 首批支持常驻/手动，按需启动按协议逐项验收。
- 首批 H.264/AAC 兼容输出；WebRTC 音频单独验证，AAC 不等于 WebRTC 有声兼容。
- 派生输出不自动创建摄像机、录像计划或递归转码。
- 默认关闭，缺依赖不阻止 NVR 主服务启动。
- 不开放任意命令/pipeline，不挂载 Docker socket；不默认跨后端或硬件到软件降级。

## 核心验收

- [ ] 输出经真实协议取回并解码，不以进程启动成功作为通过。
- [ ] 两个消费者只运行一个任务，关闭一个不影响另一个。
- [ ] 无音轨、错误路径、缺插件、无编码器、配额超限、输出超时均有明确反馈。
- [ ] 源断流、子进程异常、媒体卡死、引擎/NVR 重启均能恢复或明确失败，无残留进程。
- [ ] 更新/删除/并发启动和旧 generation 回调通过 race 测试。
- [ ] 原始流和录像默认行为不变，派生流不自动录像或递归转码。
- [ ] 鉴权开启后的拉流/发布/播放通过，无权限/跨源请求被拒绝，日志不泄露凭据。
- [ ] FFmpeg/GStreamer、本地/Docker 按支持矩阵实测，记录版本与架构。
- [ ] NVR 网页、外部播放、HA 实际验证；HA 实体身份保留。
